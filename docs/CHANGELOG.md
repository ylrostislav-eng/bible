## [Unreleased]

### Добавлено

- Рейтинг игроков: `GET /users/leaderboard` — топ-50 по рейтингу (сортировка
  по `rating`, при равенстве — по дате регистрации), плюс место текущего
  пользователя отдельным полем `me`, если он не попал в топ. Аккаунты без
  никнейма (не прошедшие онбординг) в список не попадают. Фронтенд: вкладка
  "Рейтинг" — реальный список вместо заглушки "в разработке", с подсветкой
  своей строки и отдельной карточкой "Ваше место", если оно вне топ-50.

- `POST /auth/dev-login` принимает `slot` (1-5, по умолчанию 1) — каждый
  слот логинит в отдельного тестового пользователя (`dev_user_1` …
  `dev_user_5`). Фронтенд читает `?devSlot=N` из URL. Позволяет
  протестировать дуэль вдвоём на одной машине: обычная вкладка (слот 1) +
  вкладка с `?devSlot=2`, без второго Telegram-аккаунта.
- Конфигурация для деплоя: `apps/api/Dockerfile` (сборка backend для
  Railway — устанавливает зависимости, собирает `packages/shared` и
  `apps/api`, при старте контейнера прогоняет `prisma migrate deploy`),
  `.dockerignore`, корневой `vercel.json` (сборка frontend для Vercel —
  сначала `packages/shared`, потом `apps/web`, иначе Next.js не соберётся
  из-за зависимости на общий пакет). Пошаговая инструкция — в новом
  `docs/deployment.md`: Railway для backend/PostgreSQL/Redis, Vercel для
  frontend, настройка Telegram-бота через @BotFather (кнопка меню
  открывает Mini App по адресу с Vercel).

### Архитектурные решения

- Railway выбран для backend вместо, например, Render — там PostgreSQL,
  Redis и сам сервис живут в одном проекте с общим интерфейсом, что проще
  для дальнейшего сопровождения; Render тоже подошёл бы, но с бесплатным
  веб-сервисом, который "засыпает" при простое — для игры с опросом
  состояния (дуэли) это создавало бы задержки после бездействия.
- Сид банка вопросов (`prisma:seed`) не запускается автоматически при
  каждом деплое (в отличие от миграций) — сид пересоздаёт все вопросы
  (`deleteMany` + `createMany`), поэтому это осознанно ручной разовый шаг
  после первого деплоя, а не часть автоматического цикла запуска.

## [0.4.0] — Этап 4: дуэли

### Добавлено

- Схема Prisma: `GameParticipant` (счёт/серия/награды одного игрока в
  сессии); `GameSession`/`GameAnswer` рефакторены на модель участников
  (соло-игра теперь тоже использует один `GameParticipant` — API для
  фронтенда не изменился). Добавлены `GameSession.mode = DUEL`,
  `inviteCode`, `currentOrder`, `currentQuestionStartedAt`,
  `timeLimitSeconds`; `GameAnswer.scoreDelta`.
- Backend: `DuelService`/`DuelController` —
  `POST /game/duel/create`, `POST /game/duel/join`,
  `GET /game/duel/:sessionId` (опрашивается клиентом), `POST .../answer`,
  `POST .../next`. Очки считаются по правильности + скорости ответа
  (сервер, не клиент, замеряет время) + серии подряд правильных ответов.
  По завершении дуэли обновляются `gamesWon`/`gamesLost` и рейтинг
  (+15/−10), помимо опыта и монет.
- `UsersService.applyGameRewards` расширен параметрами `outcome`/
  `ratingDelta` для побед/поражений/ничьих (соло-игра их не использует).
- `packages/shared`: типы дуэли (`DuelState`, `CreateDuelResponse`,
  `JoinDuelInput`, и т.д.).
- Frontend: `/play` стал экраном выбора режима; одиночная игра переехала
  на `/play/solo` без изменений в поведении. Новый `/play/duel`: создание
  дуэли с кодом приглашения, экран ожидания соперника, экран игры с живым
  счётом и индикатором «соперник ответил», разбор раунда для обоих
  игроков, итоговый экран с исходом (победа/поражение/ничья).

### Архитектурные решения

- Транспорт для дуэли — опрос (`GET` раз в ~1.2с), а не WebSocket, хотя
  ТЗ описывает realtime через WebSocket. Для дуэли на двоих это даёт тот
  же результат намного проще; `DuelService` спроектирован так, чтобы
  смена транспорта на WebSocket для комнат/турниров не потребовала
  переписывать игровую логику.
- Разрешение раунда полностью выводится из данных в БД (нет отдельных
  in-memory таймеров) — сервер проверяет истечение времени при каждом
  обращении (опросе или ответе), что переживает перезапуск сервера.
- Приглашение в дуэль — по 6-значному коду, без системы друзей (её ещё
  нет). Полноценные приглашения через список друзей и случайный подбор
  соперника по рейтингу — в одном из следующих этапов.

## [0.3.0] — Этап 3: одиночная игра

### Добавлено

- Схема Prisma: `Question` (банк вопросов), `GameSession`, `GameAnswer`.
- 40 проверенных вопросов по Ветхому и Новому Завету (`prisma/seed.ts`,
  `pnpm prisma:seed`), с разбивкой по сложности и теме.
- Backend: `GameModule` — `POST /game/solo/start` (подбор случайных вопросов
  с опциональными фильтрами по Завету/сложности) и
  `POST /game/solo/:sessionId/answer` (проверка ответа, объяснение, ссылка
  на стих, начисление очков/опыта/монет и пересчёт уровня по завершении).
- Backend: `UsersService.applyGameRewards` — единая точка начисления
  наград и пересчёта уровня, переиспользуемая будущими игровыми режимами.
- `packages/shared`: типы игры (`GameQuestion`, `StartSoloGameResponse`,
  `SubmitAnswerResult`, `GameSummary`, `Testament`/`Difficulty`).
- Frontend: `/play` — полноценный экран одиночной игры (выбор количества
  вопросов → вопрос с 4 вариантами → подсветка правильного/неправильного
  ответа, объяснение, ссылка на стих → следующий вопрос → итоговый экран
  со очками/опытом/монетами и уведомлением о повышении уровня).
- `prisma.config.ts` (взамен устаревающего `package.json#prisma`) для
  конфигурации миграций и seed-команды.
- `POST /auth/dev-login` — вход тестовым пользователем без Telegram-бота
  и туннеля, для локальной проверки в обычном браузере. Кнопка на
  фронтенде рендерится только при `NODE_ENV !== 'production'` и
  вырезается из продакшен-сборки (dead code elimination); бэкенд
  дополнительно возвращает 403, если `NODE_ENV === 'production'`, — то
  есть отключено даже при прямом вызове API.

### Архитектурные решения

- `GameSession.userId` — единственный владелец; для дуэлей/комнат
  потребуется отдельная таблица участников, а не переиспользование этого
  поля (см. `docs/architecture.md`).
- Открытие полного текста стиха ("кнопка открытия текста" из ТЗ) отложено
  до этапа "Изучение", где появится сам текст Библии — сейчас показывается
  только ссылка на стих (книга/глава/стихи), без выдуманной кнопки в никуда.
- Восстановление игровой сессии после перезагрузки Mini App не реализовано —
  сознательно, чтобы не усложнять API ради редкого сценария на этом этапе.

## [0.2.0] — Этап 2: авторизация и профиль

### Добавлено

- Схема Prisma: модель `User` (профиль, статистика игр, рейтинг, уровень,
  опыт, монеты).
- Backend: авторизация через Telegram Mini Apps `initData` (валидация HMAC,
  проверка срока действия) с выдачей JWT.
- Backend: `UsersModule` — `GET /users/me`, `PATCH /users/me` с валидацией
  DTO (никнейм, аватар, страна, язык).
- Backend: глобальные модули `PrismaModule`, `RedisModule`; `GET /health`
  (проверка БД и Redis).
- Backend: валидация переменных окружения (`class-validator`), глобальный
  `ValidationPipe`, CORS.
- Frontend: TailwindCSS v4, тёмная тема, mobile-first layout под Telegram
  Mini Apps (safe-area, viewport-fit=cover).
- Frontend: интеграция `@telegram-apps/sdk-react`, `AuthProvider` (вход по
  `initData`, состояния loading/no-telegram/error/authenticated).
- Frontend: онбординг (никнейм, страна, язык), профиль (реальная
  статистика), настройки (редактирование профиля).
- Frontend: нижняя навигация (Главная, Играть, Рейтинг, Друзья, Профиль);
  Играть/Друзья/Рейтинг/Турниры/Изучение — честные страницы "в разработке".
- `packages/shared`: общие типы профиля, список языков и стран,
  переиспользуемые фронтендом и бэкендом.
- Redis используется для presence-ключей (фундамент для статуса "онлайн").
- Docker Compose: добавлен сервис Redis.
- Husky + lint-staged, `.editorconfig`, `docs/`, `scripts/setup.sh`.

### Архитектурные решения

- Нижняя навигация ограничена 5 вкладками вместо 8 (см. `docs/architecture.md`).
- Аватар по умолчанию берётся из Telegram при первом входе; кастомный
  аватар — по прямой ссылке (без файлового хранилища, чтобы не усложнять
  этот этап).
- JWT-гвард не зависит от `UsersModule` (нет циклических зависимостей
  между модулями).
